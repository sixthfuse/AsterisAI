## Decision

The failed browser transcript was a real validation failure. The earlier 18/18 result did not prove browser/runtime parity. It exercised the v2 engine through an internal harness and did not prove which endpoint, client bundle, process, or loaded files produced the browser answers.

The distinctive failed-answer phrases are generated by `ai_advisor.py`, the legacy implementation behind `POST /advisor`, rather than by `advisor_v2.py`. The current v2 client posts only to `/advisor-v2`, and the current server contains one `/advisor-v2` POST route. Historical browser address-bar and network records were not retained, so the audit cannot honestly distinguish a legacy `/app` visit from a stale client bundle that posted to `/advisor`. It can prove that the displayed failed answers came from the legacy answer generator.

That runtime mismatch was not the only problem. A first live replay against the real current v2 engine found architecture gaps that the older acceptance corpus missed. The correction therefore covers runtime provenance, real-route parity, and the v2 semantic confirmation/execution boundary.

## Common root causes

1. **The validation layers were conflated.** Internal function success was reported as browser success without proving the HTML, JavaScript, endpoint, server process, session state, loaded source files, or build fingerprint.
2. **The legacy path decides too early.** `ai_advisor.py` contains keyword and special-case branches that can shape an answer before richer interpretation and deterministic eligibility evaluation. Literal title/search cues such as “computing” and “Red Seal” can therefore outrank the actual task.
3. **The initial v2 semantic boundary was incomplete.** Sol could propose a subject family, specific program, course request, or eligibility task, but deterministic confirmation sometimes treated a family as an exact program, trusted a noncanonical area string, or lost the family across a follow-up.
4. **Retrieval capabilities were too narrow.** Family discovery used program titles too heavily, broad course discovery did not exist, and composite area proposals required exact taxonomy aliases.
5. **Conversation state lacked the information needed for semantic follow-ups.** Candidate IDs were carried, but the discovery query was omitted from the compact model context. Credential replies such as “degree” had no deterministic candidate-selection capability.
6. **The earlier acceptance suite did not encode the browser transcript end to end.** It missed endpoint parity, stale-client detection, server-session behavior, composite area proposals, aviation family retrieval, campus questions, and the specific math-option eligibility rule.

## First divergence in the newest browser transcript

The first divergence was before the database and before answer synthesis: the failed browser answers entered the legacy `/advisor` generator. Their text fingerprints occur in `ai_advisor.py`, including the “matching programs,” generic Red Seal, and “saved topic applies” response forms. They do not originate in the v2 semantic-first executor.

The first live replay of the real v2 engine then exposed its own earliest semantic/executor divergence on the nursing discovery turn: Sol proposed a legitimate family, but deterministic confirmation treated the proposal as though it had to be an exact institutional taxonomy key or program entity. That caused a failure before the appropriate family capability could run. Later divergences had the same shape: a structured semantic proposal reached a deterministic boundary that lacked a general confirmation capability.

## Architecture correction

The experimental path now follows this sequence:

1. Sol interprets the current message into a structured plan: intent, question class, scope, proposed program/course/subject, reference behavior, requested facts, and student facts.
2. Deterministic code normalizes conflicts in that plan and gives explicit current-message meaning priority over saved context.
3. Proposed entities and academic areas are confirmed against PostgreSQL data or the institutional taxonomy abstraction.
4. A bounded capability performs the authoritative work: taxonomy discovery, family discovery, course discovery, campus lookup, international availability, program facts, or deterministic admission evaluation.
5. The answer is synthesized only from the verified capability result. Deterministic eligibility remains authoritative.

The following components were rebuilt or added:

- A bounded program-family capability that searches curated names and descriptions rather than relying on title matches alone.
- Institutional taxonomy confirmation for Engineering and Computing & IT, including composite semantic proposals such as “structural, civil, or other engineering.”
- A bounded course-discovery capability joined to program and area relationships.
- Deterministic credential selection within the candidates already shown, so “degree” resolves the Construction Management degree without a new global search.
- Durable discovery-query context for follow-ups such as “which of these” and “aviation programs.”
- Eligibility intent normalization so a named program plus applicant facts and an eligibility question reaches deterministic rule evaluation even when “Red Seal” is present.
- Math-option evaluation for accepted Math 11 aliases when the stored alternative rule has no subject identifier.
- Campus/main-campus and phone capabilities backed by the campus directory.
- Runtime diagnostics and response provenance: build fingerprint, startup time, process ID, executable, working directory, route ID, model setting, loaded module paths and hashes, request ID, session ID, capability path, and decision path.
- Cache prevention and a versioned v2 client asset so a stale browser bundle is visible and less likely.

No per-question answer branches were added for the transcript. The fixes operate on reusable concepts: family versus entity, composite area confirmation, course versus program scope, candidate credential selection, current-message priority, and eligibility authority.

## Real-route parity proof

The permanent parity test starts a separate real Uvicorn process and exercises HTTP rather than calling the advisor function directly. It verifies:

- exactly one `/advisor-v2` POST route;
- the loaded `main.py`, `advisor_v2.py`, and `advisor_v2_sol.py` paths;
- `/app-v2` is uncached and loads only the versioned v2 JavaScript client;
- the client posts to `/advisor-v2`, never `/advisor`;
- request and session IDs survive the HTTP boundary;
- server-carried state is used after the first turn;
- all 23 newest transcript turns execute over one server session;
- the exact semantic capability and decision path for the critical turns;
- legacy response signatures are absent.

The audit harness supports three explicit modes using the same transcript: internal function execution, direct HTTP with client-carried state, and browser-equivalent HTTP with server-carried session state. This makes future divergence visible instead of treating those paths as interchangeable.
